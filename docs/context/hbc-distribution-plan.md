# HBC Distribution Plan

## Problem

This **personal fork** (`com.daverui.michelly`, built from local source) is not installed from the LG
Content Store, and there is no sideload-by-hand workflow that scales to updates. The target TV already
runs **Homebrew Channel (HBC)**, which installs only what a repository document advertises. Without
such a document the app can be installed once but never updated.

## Solution

The fork is distributed through a **custom HBC repository**: a single JSON document,
`{"packages":[...]}`, served over **HTTPS**. HBC fetches it, reads the `data.packages` array — never
`pkgList` — and offers each package for install or update.

### Repository document

- Served over **HTTPS** only; HBC will not read a plain-HTTP repository.
- Root shape is exactly `{"packages":[...]}`.
- HBC reads **`data.packages`**; a `pkgList` key is ignored (a common copy-paste failure).

### Our repository (live)

| Item | Value |
| --- | --- |
| **Source URL (paste on the TV)** | `https://daver-ui.github.io/webos-hub/repo.json` |
| Host | GitHub **Pages**, source branch `gh-pages`, path `/` (site root `https://daver-ui.github.io/webos-hub/`) |
| Package | `com.daverui.michelly` (`MiChelly`), version `1.3.2`, `type: "web"`, `rootRequired: false` |
| IPK | `https://daver-ui.github.io/webos-hub/ipk/com.daverui.michelly_1.3.2_all.ipk` (sha256 `af4e544a490eb5f0710d90136c93f5221fbbdd8ac2e880777ecd61ad6a6c1373`) |
| Icon | `https://daver-ui.github.io/webos-hub/icons/michelly.png` |
| Remote app bundle | `https://daver-ui.github.io/webos-hub/app/manifest.json` + the 9 payload files under `app/` |

The version and sha256 above are a **snapshot**: the Build workflow rebuilds `gh-pages` on every push
to `master`, so they update automatically on the next such push (see [Update flow](#update-flow)).
Treat them as illustrative, not constants.

The document is generated by `npm run repo` (`tools/gen-repo.js`), which emits the `ipkHash.sha256`
matching the built IPK. The IPK is served from `ipk/`; Pages sends `access-control-allow-origin: *`.

### Package entry

| Field | Value |
| --- | --- |
| `id` | `com.daverui.michelly` |
| `title` | `MiChelly` |
| `iconUri` | HTTPS URL of a PNG icon |
| `manifest` | Embedded manifest object (preferred over `manifestUrl`) |
| `rootRequired` | `false` |

Embed the `manifest` rather than pointing at a `manifestUrl`: GitHub *release assets* do not send
`access-control-allow-origin`, so a separate manifest fetch fails from HBC's webview.

### Manifest

| Field | Value |
| --- | --- |
| `id` | `com.daverui.michelly` |
| `version` | must equal `version` in `frontend/appinfo.json` (generated by `npm run version`) |
| `type` | `"web"` — there is **no** `type: "service"` |
| `title` | `MiChelly` |
| `iconUri` | HTTPS URL of a PNG icon |
| `ipkUrl` | HTTPS URL of the `.ipk` |
| `ipkHash` | `{"sha256":"<64 lowercase hex>"}` of that exact IPK |

`tools/gen-manifest.js` (run by `npm run manifest`) generates
`build/com.daverui.michelly.manifest.json` with `id`, `version`, `type`, `title`, `appDescription`,
`rootRequired: false`, `ipkUrl` (the bare filename) and the computed `ipkHash.sha256`. It points
`iconUri`/`sourceUrl` at the fork's host and repository, and `ipkUrl` is only a filename — it is
**not** a full repository-document generator. Use `tools/gen-repo.js` (`npm run repo`) for the
`{"packages":[...]}` document with real HTTPS URLs.

### One IPK for app and service

The bundled Luna discovery service ships **inside the same IPK** as the web app. `npm run package`
runs `ares-package --no-minify --outdir build/ services frontend`, producing
`build/com.daverui.michelly_<version>_all.ipk` (architecture-independent).

`rootRequired: false` is correct: registering a bundled service is not an elevation. The service runs
non-elevated, binds no privileged resource and only performs UDP discovery on the local network. Only
a service that needed privilege escalation would require root.

### Remote app bundle (`app/`)

The same `gh-pages` site also serves the **remote app bundle** that the thin loader fetches at launch
(see [architecture](architecture.md#thin-loader--remote-bundle)):

| Path | Contents |
| --- | --- |
| `app/manifest.json` | `{schema:1, bundleVersion, appVersion, files:[{path,type,size,sha256}]}` |
| `app/js/app/{platform,api,auth,ui,catalog,player,audio}.js` | Payload JS, byte-for-byte copies of `frontend/js/app/…` |
| `app/js/index.js` | Payload picker/flow JS |
| `app/css/app.css` | Payload stylesheet |

The bundle is generated by `npm run bundle` (`tools/gen-bundle.js`) — deterministic and idempotent,
with a `--check` mode — and published by the Build workflow's **Generate remote app bundle** step,
which copies `build/app/**` into `gh-pages/app/`.

**What auto-updates vs what does not:**

- Code/UI in the 9 payload files goes **live on the TV's next launch** — no HBC interaction, no IPK
  download, no reinstall. GitHub Pages caches responses for roughly 10 minutes, so a publish is not
  instantly visible to every TV.
- The **IPK itself still needs the manual HBC refresh**: the version string is frozen in
  `frontend/appinfo.json`, and changes to `frontend/index.html`, `js/loader.js`, `js/lib/sha256.js`,
  `js/ajax.js`, `js/storage.js`, `webOSTVjs-1.2.11/`, `frontend/appinfo.json`, `frontend/assets/` or
  the bundled Luna service only reach the TV through a newly installed IPK.

**Integrity, not authenticity.** The loader verifies each payload file's size and sha256 against
`app/manifest.json`. That proves the bytes match the manifest; it does **not** sign or authenticate
them — control of the HTTPS host is the real trust boundary, exactly as with the IPK's
`ipkHash.sha256` (see [Common mistakes](#sha256-proves-integrity-not-authenticity)).

**Deferred:** a rooted boot-hook poller (`luna://org.webosbrew.hbchannel.service/install`) is **not
implemented**; the TV fetches the manifest only on launch.

### Update flow

1. Bump `version` in `package.json`, then run `npm run version` (mandatory — see Common mistakes).
2. `npm run check` → `ares-package --check`; expect `no problems detected`.
3. `npm run package` → `build/com.daverui.michelly_<version>_all.ipk`.
4. `npm run repo` → `build/repo.json` (`{"packages":[...]}`, embedded `manifest`, HTTPS `ipkUrl` /
   `iconUri`, recomputed `ipkHash.sha256`). `npm run manifest` still emits the standalone manifest if
   needed.
5. Confirm the generated document: embedded `manifest`, `type: "web"`, `rootRequired: false`, the
   correct `ipkHash.sha256`, and HTTPS `ipkUrl` / `iconUri`.
6. Commit and push to `master` (or run the **Build** workflow via `workflow_dispatch`). CI builds the
   IPK, regenerates `repo.json`, generates the remote app bundle (`npm run bundle`) and publishes
   `repo.json` + the IPK + `app/**` to the **HTTPS static host** automatically — for this fork, the
   GitHub Pages `gh-pages` branch (see
   [release protocol](../protocols/release-protocol.md#6-publish-to-the-https-static-host)). The
   `Publish to gh-pages` step does **not** run on a GitHub **release**; publishing by hand is the
   fallback only. GitHub **Pages** is verified to send `access-control-allow-origin: *`; GitHub
   **release assets** do not — hence the embedded manifest.
7. On the TV, refresh the repository view in HBC and choose **Update** — needed only for shell/service/
   IPK changes. A payload-only code/UI change ([Remote app bundle](#remote-app-bundle-app)) reaches the
   TV on its next launch without any HBC interaction.

HBC has **no auto-update**: the view must be refreshed manually, and GitHub Pages caches responses for
roughly 10 minutes.

### Known limitation: no deep links

`frontend/appinfo.json` declares no `handles`, `launchParams` or `params`, and the app reads no launch
arguments. It has no deep-link surface of its own — a launch always lands on the server picker (or
auto-connects to the last server). See [architecture](architecture.md#no-launch-parameter--deep-link-surface).

### Tooling (implemented)

- **`tools/gen-repo.js`** — implemented: generates the `{"packages":[...]}` document from
  `frontend/appinfo.json` plus the built IPK, computing `ipkHash.sha256` and HTTPS URLs. `baseUrl`
  defaults to `https://daver-ui.github.io/webos-hub`; override it via argv or `$HBC_REPO_BASE_URL`.
  Refuses to run until `npm run package` has produced the IPK.
- **`npm run repo`** — implemented: runs `node tools/gen-repo.js`, writing `build/repo.json` from the
  built IPK. It runs in CI (the `Generate repository document` step), so a local run is only for
  pre-flight inspection.
- **`tools/gen-bundle.js`** — implemented: writes the remote app bundle (`build/app/manifest.json` +
  the 9 payload files, byte-for-byte) that the thin loader fetches. Deterministic and idempotent;
  `--check` fails when `manifest.json` is stale. No IPK required.
- **`npm run bundle`** — implemented: runs `node tools/gen-bundle.js`. It runs in CI (the **Generate
  remote app bundle** step); a local run is only for pre-flight inspection.
- **`.github/workflows/build.yml`** — automated publish: on `push` to `master` or `workflow_dispatch`
  it builds the IPK, runs `npm run repo`, runs `npm run bundle` and pushes `repo.json`, the IPK and
  `app/**` to `gh-pages`. It also
  fails the run when `package.json` and `frontend/appinfo.json` disagree on the version. See
  [release protocol §6](../protocols/release-protocol.md#6-publish-to-the-https-static-host).
- Publishing by hand (placing `repo.json`, the IPK, the `app/` bundle and the icon on the host) is now
  only a **fallback** for a failed CI run or a manual publish.

## When to use

- Shipping or updating this fork to TVs that already run Homebrew Channel.
- Preparing a release artifact (`repo.json` plus the IPK) for an HTTPS static host.

## When not to use

- TVs without Homebrew Channel — this path does not sideload without it.
- Distribution of the upstream app through the LG Content Store, which is out of scope for the fork.
- Local development: build and install directly with `npm run deploy` / `npm run launch`.

## Examples

A minimal repository document for this fork:

```json
{
  "packages": [
    {
      "id": "com.daverui.michelly",
      "title": "MiChelly",
      "iconUri": "https://daver-ui.github.io/webos-hub/icons/michelly.png",
      "rootRequired": false,
      "manifest": {
        "id": "com.daverui.michelly",
        "version": "1.3.2",
        "type": "web",
        "title": "MiChelly",
        "iconUri": "https://daver-ui.github.io/webos-hub/icons/michelly.png",
        "ipkUrl": "https://daver-ui.github.io/webos-hub/ipk/com.daverui.michelly_1.3.2_all.ipk",
        "ipkHash": { "sha256": "<64 lowercase hex>" }
      }
    }
  ]
}
```

The `version` and `ipkUrl` above mirror the live snapshot; `npm run repo` always emits the current
version. `<64 lowercase hex>` is the digest of the IPK being published — regenerate it every release;
never reuse a previous hash.

Generating the layout and confirming the hash:

```bash
npm run package                     # -> build/com.daverui.michelly_<version>_all.ipk
npm run repo                        # -> build/repo.json (HTTPS URLs + ipkHash.sha256)
sha256sum build/com.daverui.michelly_<version>_all.ipk
# the digest must equal ipkHash.sha256 in build/repo.json
```

## Common mistakes

### Homebrew Channel shows an Update that never goes away

HBC compares version **strings by equality**, not by semver. If `frontend/appinfo.json` still says the
old version while the manifest advertises a new one, HBC believes the installed version differs from
the published one and offers an update forever. Always bump `version` in `package.json` and run
`npm run version` before pushing. CI's version-consistency gate fails the Build run when those two
files disagree, so drift is never published silently.

### HBC update fails after downloading the whole package

A wrong `ipkHash.sha256` is detected only **after** the full IPK download, so the failure looks like a
network problem. Recompute the hash after every build (`npm run repo` recomputes it in
`build/repo.json`) and never reuse a previous hash. The digest must be 64 lowercase hex characters.

### Publishing `build/com.daverui.michelly.manifest.json` as the repository document

That file is a single *manifest*, not a `{"packages":[...]}` repository. `ipkUrl` is a bare filename
and `iconUri` points at the fork's host, not a repository document. HBC needs the repository document wrapping the manifest with real
HTTPS URLs — generate it with `npm run repo`.

### sha256 proves integrity, not authenticity

HBC verifies the IPK against `ipkHash.sha256`. That guarantees the file matches the repository
document; it does **not** sign or authenticate the package. Control of the HTTPS host is the real
trust boundary.

### There is no IPK auto-update

HBC re-reads the repository only when its view is refreshed, and GitHub Pages caches responses for
roughly 10 minutes. Plan IPK communication around a manual refresh, not a push notification. The
**remote app bundle is different**: it is fetched on every launch, so payload code/UI changes appear by
themselves on the next launch.

### Expecting an HBC Update for a payload-only change

If only the 9 payload files changed, `npm run bundle` + a push refreshes `gh-pages/app/` but the IPK
version string stays the same, so HBC shows no Update — the new code/UI is already live on the next
launch. A version bump + HBC Update is only needed when the shell, service, assets or `appinfo.json`
change.

### The build toolchain differs from upstream CI

Upstream CI (`.github/workflows/build.yml`) uses Node 14.x and installs `@webosose/ares-cli` globally,
whereas this fork builds locally with the devDependency (`^2.4.0`) on a much newer Node. If a build
behaves differently from CI, check the Node/ares version first.
